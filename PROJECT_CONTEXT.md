# Anti-Порожняк — Mangystau Hackathon

Контекст проекта для Claude Code. Прочитай целиком перед началом работы.

---

## Что делаем

**Система предотвращения порожних рейсов для внутрирегиональных перевозок
Мангистауской области.**

Не биржа перевозок. Не «Uber для грузовиков». Позиционирование другое:

> Мы не ищем перевозчика. Мы устраняем пустой обратный рейс.

Цепочка продукта:

```
Сообщение человека («нужно завтра из Актау в Шетпе 5 тонн кирпича»)
   ↓ LLM превращает текст в структурированную заявку
Груз в БД
   ↓ поиск грузов ВДОЛЬ КОРИДОРА движения машины
Детерминированный скоринг
   ↓
Обратная загрузка
   ↓
Empty KM Saved → литры → тенге
```

## Ключевая находка: асимметрия грузопотока

**Это то, что отличает нас от остальных команд. Не потерять при реализации.**

В Мангистау грузопоток однонаправленный. Из Актау в посёлки везут всё:
продукты, стройматериалы, FMCG, воду. Обратно в Актау — почти ничего.

Значит наивный поиск «точка в точку» найдёт **ноль** обратных грузов
Бейнеу → Актау. Обычные биржи здесь умирают.

На защите обязательно спросят: «что именно повезут обратно, воздух в коробках?»

**Три механизма, которые дают обратную загрузку:**

**1. Инверсия типов груза.** Обратно идёт не коммерческий товар, а:
- возвратная тара ритейлеров и дистрибьюторов напитков
- строительная опалубка, леса, спецоборудование с завершённых объектов
- вторсырьё, картон, металлолом, изношенные шины (в Актау — пункты переработки)

→ В форме и в LLM-парсере отдельные категории: `возвратная тара`,
`оборудование`, `вторсырьё`, `лом`.

**2. Дисконтированный тариф.** Перевозчику всё равно возвращаться, его
альтернатива — сжечь топливо впустую. Обратный рейс предлагается со скидкой
50–60%, что перекрывает солярку. Отправителю из посёлка выгодно: цена втрое
ниже отдельной машины.

→ Подсказка при создании заявки из посёлка: «обратный коридор, рекомендуемая
цена −60% от стандартной».

**3. Цепочки вместо прямых плеч.** Машина из Бейнеу может взять груз до Шетпе,
там сбросить, взять тару до Жанаозена, оттуда уйти на Актау. Три коротких
плеча реальнее одного длинного.

→ Это и есть алгоритм по коридору.

## Алгоритм матчинга

**Плохо (так делают все):**

```
машина: Актау → Жанаозен
груз:   Жанаозен → Актау
        совпало? матч
```

При асимметрии это даёт ноль результатов.

**Правильно:**

```
коридор машины: Актау ──── Жанаозен ──── Шетпе ──── Актау
                              │
                              └── груз лежит ВНУТРИ коридора
```

Груз подходит, если он лежит на пути возвращения с приемлемым отклонением,
а не если его конечные точки совпали с маршрутом машины.

**Скоринг — детерминированный и объяснимый:**

```
Match Score =
  40%  покрытие маршрута
  25%  минимальное отклонение (detour)
  20%  совместимость груза и типа кузова
  10%  временное окно
   5%  экономический эффект
```

В интерфейсе рядом со score показывать разбор:

```
Почему этот груз?
  92% маршрута совпадает
  7 км отклонение
  подходит кузов
  временное окно совпадает
```

Объяснимый алгоритм здесь **сильнее** ML-ранжирования: диспетчер понимает
решение, а на защите нет вопроса «на чём обучали».

## Где ИИ — и где его НЕ надо

### ✅ LLM-парсер заявки — единственное место ИИ в MVP

Кейс прямо называет боль: заявки идут через звонки и мессенджеры.

Пользователь пишет или диктует:

> «Нужно завтра из Актау в Шетпе отвезти 5 тонн кирпича, машина с тентом»

LLM возвращает структуру:

```json
{
  "origin": "Актау",
  "destination": "Шетпе",
  "cargo": "кирпич",
  "cargo_category": "стройматериалы",
  "weight_tons": 5,
  "vehicle_type": "тент",
  "date": "2026-08-20"
}
```

Пользователь подтверждает → заявка создана.

Формулировка для защиты:

> Мы не используем ИИ для решения, которое можно объяснить формулой.
> Мы используем LLM там, где входные данные изначально неструктурированные —
> сообщения от диспетчеров и водителей.

### ❌ Чего НЕ делать с ИИ

- **ML-ранжирование матчей.** Нет обучающих данных, нет истории сделок.
  Любая «модель» — либо та же формула в костюме, либо выдумка.
  Первый вопрос жюри: «на чём обучали» — и ответа нет.
- **Предсказание цены.** Та же проблема.
- **AI-чат-бот.** Самый очевидный способ получить «а зачем здесь AI».

## Экономика — требование 06

**Главная метрика: Empty KM Saved.** Всё остальное производные.

```
146 км сэкономленного порожнего пробега
   ↓ × расход 30 л/100 км
43.8 литра
   ↓ × цена дизеля
13 140 ₸
```

**Правила расчёта:**

- Считаем **только топливо**. Амортизацию и время упоминаем словами как
  дополнительный эффект, но не включаем в цифру — их нечем обосновать.
- Каждое допущение подписано в интерфейсе.
- Не экстраполировать («при 100 матчах в день сэкономим миллион») — это
  выдуманная сотня матчей. Считаем один рейс честно.

**Блок Calculation прямо в UI** — обязательно:

```
Empty distance before:  300 km
Empty distance after:   154 km
EMPTY KM SAVED:         146 km
Vehicle consumption:    30 L/100 km
Fuel saved:             43.8 L
Fuel price:             300 ₸/L*
Fuel saving:            13 140 ₸*
                        * demo assumptions
```

> **Правило команды:** ни одной цифры в продукте и презентации, которую
> нельзя объяснить за 10 секунд. Для каждой — источник или явное допущение.

## Стек и структура данных

```
React (Vite) + Leaflet
        ↓
FastAPI
        ↓
PostgreSQL
```

**Без PostGIS.** Регион конечный: 10 узлов и матрица расстояний в JSON.
Карта — только визуализация результата, не источник вычислений.

### Четыре таблицы, не больше

```sql
users     -- id, name, role (sender | carrier | dispatcher)

vehicles  -- id, owner_id, vehicle_type, capacity_tons,
          -- origin, destination, departure_time, status

loads     -- id, sender_id, origin, destination, cargo_type,
          -- cargo_category, weight_tons, required_vehicle,
          -- pickup_time, price_kzt, status

matches   -- id, vehicle_id, load_id, score, detour_km,
          -- empty_km_saved, fuel_saved_l, fuel_saved_kzt, status
```

Таблица `matches` должна реально существовать в БД — на защите это
доказательство, что матчинг не анимация на фронте.

**Статусы:** `OPEN → ACCEPTED → IN_TRANSIT → DELIVERED`. Меняются в БД,
второй пользователь видит изменение.

### Данные региона

`locations.json` — узлы с координатами:
Актау, Жанаозен, Форт-Шевченко, Курык, Бейнеу, Шетпе, Мунайлы,
Таучик, Сайотес, Акшукур.

`routes.json` — матрица: `distance_km`, `estimated_time`, `road_type`.

**Seed на 40 рейсов с реалистичной асимметрией:** из Актау — крупные
коммерческие грузы, обратно — мелкие, дешёвые, категории возвратные.
Пустая база на демо убивает проект.

## Сценарий демо — 60 секунд

Отрепетировать. Не импровизировать.

```
0–5 сек    Человек пишет сообщение обычным языком
           «нужно завтра из Актау в Шетпе 5 тонн кирпича»

5–10 сек   Заявка создана. Найдено 3 машины

10–20 сек  ВТОРОЕ ОКНО: перевозчик видит 87% match
           Нажимает «Взять груз»
```

## Три места, где проект почти наверняка провалится

Все три названы независимо тремя разборами. Держать в голове постоянно.

### 1. Увязнуть в карте

Соблазн потратить 8 часов на красивые линии, анимации, слои, роутинг по
реальным дорогам. Получится красивый экран и не получится продукт.

**Порядок работ строго:** БД → API → матчинг → экономика → UI → карта.
Карта последняя и тупая.

Не строить честный маршрутизатор по грунтовкам. Прямые линии или OSRM.

### 2. Демо двух ролей оставить на последние часы

Требование 05 требует показать: заявка → перевозчик берёт → диспетчер видит.
Легко обнаружить в последний час, что состояние не синхронизируется.

**Проверить в первой половине разработки, контрольная точка 19 августа 20:00:**
два браузера, изменение состояния в одном видно во втором, данные из БД.

Реализация: HTTP-поллинг раз в 2 секунды. Не WebSocket — лишняя сложность.
На демо: Chrome для отправителя, Incognito для перевозчика.

Никаких `setTimeout(() => status = "accepted")`.

### 3. Пустая база и необъяснимые цифры

Seed на 40 рейсов должен быть готов **до** финального прогона.

На прошлом хакатоне мы показали объект в 4261 м от воды при скорости
7.58 м/год — числа противоречили друг другу, и это заметили. Здесь такого
быть не должно: блок Calculation в UI и правило десяти секунд.

## Формулировка для питча

Не говорить: «мы создали цифровую платформу грузоперевозок Мангистау».
Звучит как ещё один стартап из акселератора.

Говорить:

> В Мангистау проблема не в том, что грузу нужна машина. Проблема в том,
> что машина после доставки возвращается пустой. И главный секрет региона:
> обратно в Актау грузов почти нет — простые биржи здесь умирают.
>
> Мы не ищем несуществующие товары. Мы монетизируем обратный путь за счёт
> возвратной тары, вторсырья и коротких цепочек между посёлками по сниженному
> тарифу.
>
> Результат измеряется в одной цифре: Empty KM Saved.
